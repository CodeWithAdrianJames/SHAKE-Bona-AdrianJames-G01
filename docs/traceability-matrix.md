# SHAKE — End-to-End Requirements & Hardening Traceability Matrix (PD3)

This matrix traces every SDD functional requirement (`F-01`–`F-11`), every business rule (`BR-01`–`BR-13`), and every Project Development 3 hardening requirement to the specification, code, routes, schema, and automated tests that implement and verify it.

All paths are relative to the repository root. Test references name the **test class** and, where one class covers several requirements, the specific **test method**.

## Test File Legend

| Tag | Test module | Tests | Scope |
| --- | --- | ---: | --- |
| **A** | `accounts/tests.py` | 46 | Users, registration, email login, profile, password change, API tokens |
| **C** | `contracts/tests.py` | 66 | Schema constraints, ingestion pipeline, stitching, CRUD, archiving, exports, carrier admin, loopback API |
| **H** | `contracts/test_hardening.py` | 35 | PD3 hardening pass: error pages, settings, access control, template audit, validation, integrity, query counts |
| **P** | `contracts/tests_pd3_hardening.py` | 62 | Dedicated PD3 rubric verification suite (one class per PD3 requirement or PD1 feature) |
| **D** | `dashboard/tests.py` | 9 | Role dashboards, role guards, live metrics |
| | **Total** | **218** | All discovered by `manage.py test` (default `test*.py` pattern) |

Run the full suite with `python manage.py test` (PostgreSQL via `.env`) or `$env:DATABASE_URL=" "; .\.venv\Scripts\python.exe manage.py test -v 2` (local SQLite). See [`README.md`](../README.md#running-the-automated-test-suite).

> **Spec numbering note:** feature-spec file numbers (`01`–`11`) are not the same as SDD feature IDs. For example, spec `02` covers `F-03` and spec `06` covers `F-04`. The table below maps each feature ID to the spec file that actually defines it. `F-02` (Carrier Profile Management) has no dedicated spec file; it is defined in `docs/context/project-overview.md` and enforced by `BR-03`. Spec `08` defines the core persistence architecture shared by all features.

ON DELETE`); **Model** = field validator or `Model.clean()` (run by every ModelForm, the Django admin, and `full_clean()`); **Form** = form `clean_*` method; **Service** = ingestion/export service; **View** = view-level guard.

## 4. Known Verification Gaps

These items are implemented but have no dedicated automated test. They are listed so the matrix does not overstate coverage; adding tests is outside the scope of this documentation pass.

1. **`/media/` URL pattern** — `shake/urls.py` exposes only `media/profile_photos/` in DEBUG. Tests run with `DEBUG=False`, so the pattern is never registered under test. It was verified manually (`runserver`, `DEBUG=False`).
2. **`BR-11` `ON DELETE RESTRICT` on `ContractMetadata.carrier`** — declared in the schema, but no test deletes a referenced `CarrierProfile`. The UI only deactivates carriers.
3. **`ArbitraryCharge` web CRUD** — not implemented (read-only via detail, export, and API). Its amount rule is tested at the validator and database layers only.
4. **PostgreSQL** — the full suite has not been run against PostgreSQL on this workstation (`ISS-01`); the CI `test-postgres` job is the PostgreSQL verification path.
